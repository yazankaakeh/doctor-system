# Chapter 5 — Project Review (Doctor System)

## 5.1 Project Outcomes

The main goal of the project was to build a medical consultation platform that lets doctors and patients manage appointments, consultations, and medical records in one place, without needing the patient to physically come to the clinic for every follow-up. Looking at the starting point and where the system is now, the goal was reached.

The Doctor System is a working, deployed Laravel 12 application running on PHP 8.4. Patients can register, browse doctors, book an available time slot, pay for the consultation, join a video call with the doctor through the browser, chat in real time during the appointment, and later download a PDF of the prescription or lab test order. Doctors have their own portal where they manage their weekly availability, recurring schedules, bookings, vital signs, medicines, medical tests, final diagnoses, and examination files. The whole platform supports English, Arabic, and Turkish, and the Arabic layout switches to a proper right-to-left direction across every screen, including the medical examination editor, the booking wizard, and the admin side.

All the main objectives set at the start were completed. The system architecture is modular, built on top of `nwidart/laravel-modules`, and is split into fifteen modules (Core, Auth, Doctor, Patient, Booking, Payment, Messaging, Notification, AdminManagement, Blog, CMS, SEO, Theme, Website, MCP). Authentication uses three guards (`doctor`, `patient`, `web`) so that a doctor logging in and a patient logging in go through completely separate flows without interfering with each other. The video consultation is powered by a self-hosted Jitsi Meet server on a separate VPS, reachable at meet.yupcrm.com, with a proper Let's Encrypt certificate and a CSP `frame-ancestors` policy that allows the doctor system to embed the room inside its own page. Payment supports three methods: PayPal for real card payments abroad, offline bank transfer with proof upload for local patients, and a credit-card prototype that uses a Luhn-validated sandbox to exercise the full "pay → confirm booking → create meeting room" flow without needing a real acquirer.

On the testing side, the project has two layers. The first is automated tests split into unit and feature suites — enum contract tests, the vital-signs range-check logic, the Luhn validator rule, the composer CI script itself, and regression tests for fixed bugs like the audit log polymorphic accessor. The second is a continuous integration workflow on GitHub Actions that runs Laravel Pint, PHPStan at level 5, a composer audit, and a custom translations integrity check that compares translation keys across the three languages.

The research questions were addressed as well. The platform shows that an independent developer can build a practical telemedicine system using open-source tools end to end (Laravel, Livewire, Reverb, Jitsi, nginx, MySQL), that multi-guard authentication in Laravel is workable even when the domain has several distinct user types, and that keeping the UI calm and using the theme's primary color instead of scattering colors across every section actually makes a complex medical interface feel usable rather than overwhelming.

## 5.2 Discussion of Results

The system works well for the core clinical flow. A patient can register with email or social login (Google, Facebook, X), book a slot from a doctor's calendar, pay by any of the three methods, receive a booking-confirmed notification, join the video call when the time comes, and have a prescription and list of tests ready to download at the end. On the doctor side, the medical examination editor captures everything that matters during a consultation: vital signs with in-range and out-of-range indicators, medicines with dose and dosage form, laboratory and radiology tests, final diagnoses from a reusable list, and arbitrary file attachments like lab reports. The chat stays embedded during the consultation so the doctor and patient can share text while the video is running, and the medical examination page itself sits right next to the video so the doctor is not jumping between tabs.

The most technically satisfying part was getting the Jitsi video consultation to work properly inside the application frame. Public meet.jit.si requires an authenticated moderator and blocks everyone else with a "members only" lobby, which is a non-starter for a clinic. Switching to a self-hosted Jitsi fixed that, but then the host-level nginx reverse proxy was adding `X-Frame-Options: SAMEORIGIN` from a shared `global_settings` snippet, so the iframe was refusing to render. The final fix was adding a `Content-Security-Policy: frame-ancestors` directive scoped to the specific vhost, which the browser honors over the older `X-Frame-Options` header. Once that was in place, the doctor and patient could both join from inside the application and the pre-join screen showed the correct doctor name, patient name, and appointment time pulled automatically from the booking record.

The multilingual support was the other area that took real effort. Spatie Translatable handles the JSON columns for translatable model fields, but the Arabic RTL layout needed careful work in the Bootstrap and Vuexy theme settings, and the forms and dropdowns had to be tested in all three languages because a string that fits nicely in English can wrap awkwardly in Arabic or Turkish. The CI also includes a custom `translations:integrity-check` artisan command that flattens every lang file to dot-notation keys and checks that each locale has the same set as the base locale, with a `--fix` mode that fills missing keys with `[TODO:locale]` placeholders so the gaps are obvious to translators.

Performance is good under normal usage. Livewire components update in under 300 ms on the local server, the medical examination page with seven tabs and several live components loads in one render pass, and the MySQL database on the VPS handles the current load without any visible delay. The Reverb WebSocket server handles the real-time chat and notification delivery without issues during testing.

## 5.3 Challenges Faced

Three main challenges came up during the project.

The first was the scope of the modular architecture. Fifteen modules sounds manageable in theory, but in practice every feature touches three or four of them. Booking depends on Doctor and Patient, Payment depends on Booking, Messaging is triggered by Booking confirmation, the video consultation in Core reaches into Booking to load the doctor and patient names, and so on. Avoiding circular dependencies was a constant concern. The solution was to keep most cross-module references behind `class_exists` guards and to put shared traits like `HasVideoConsultation` in the Core module so the Booking model could use them without pulling in unrelated code.

The second was the infrastructure work. Self-hosting Jitsi on a VPS required learning Docker Compose for the Jitsi stack itself, then understanding how the CloudPanel-generated nginx reverse proxy interacted with the Jitsi containers on 8000/8443, then debugging firewall rules because UDP 10000 for the video bridge was blocked, then finally fixing the `X-Frame-Options` issue mentioned above. Each of these pieces had its own documentation and error shapes, and none of it was covered in any of the courses I had taken before. The same was true for setting up the GitHub Actions CI workflow, adding the custom composer scripts, and registering the custom `luhn` validation rule inside the Payment module's service provider.

The third was keeping the code quality high across fifteen modules while also moving fast enough to actually finish. Laravel Pint and PHPStan help a lot, and having them run automatically in CI means style and type issues get caught before they pile up, but there were still many small decisions that had to be made alone — whether a method belonged in the controller or the action, whether a livewire component should own its own state or receive it from the parent, whether a feature needed a repository or could stay in the action. Those decisions add up over a codebase this size, and reviewing them was something I had to do on my own because there was no senior developer on the project.

## 5.4 Implications of the Project

The Doctor System has practical value beyond being an academic project. For patients, especially ones who live far from a specialist or cannot easily travel, the ability to book a consultation and meet the doctor over video removes real friction. They can upload their test results before the appointment, join from their phone or laptop, and walk away with a PDF prescription they can take to the pharmacy. No waiting room, no taking a day off work, and the whole history of their consultations stays in one place so the next doctor they see has context.

For clinics and independent doctors, the system lowers the cost of running a basic telemedicine operation. A clinic that would otherwise need a booking platform, a video-conferencing subscription, a messaging app, and some kind of electronic record system can run all of that from a single deployment. The offline payment with proof upload is specifically useful in markets where PayPal and credit cards are less common and bank transfer is still the norm, and the admin side gives the clinic a verification step so they stay in control of what actually gets marked as paid.

The multilingual support with proper Arabic RTL matters for the Middle East market specifically. Most of the commercial telemedicine platforms either ignore Arabic entirely or treat it as a translated string layer without addressing the layout, which means patients end up with a mirrored interface that is hard to read. Building Arabic support from the start, and testing every screen in it, was a deliberate choice that makes the system usable for a population that is often underserved by global SaaS products.

On a more general level, a consultation that happens over video instead of in person has a real environmental benefit when multiplied across thousands of patient visits. Less fuel burned, fewer paper prescriptions printed, less waste from single-use items at the clinic. None of this is the main reason to build the system, but it is a side effect that matters.

## 5.5 Limitations and Future Scope

### Limitations

The credit-card payment is a prototype. It correctly validates card numbers with the Luhn algorithm, extracts the last four digits and brand, creates a Payment row with a fake transaction ID, and moves the booking to Confirmed. But it does not communicate with a real payment service provider, which means the money is never actually captured. A production deployment would need to swap the body of `ProcessCreditCardPaymentAction` for a real Stripe or Iyzico integration before taking live traffic.

The testing is mostly developer-driven. The automated suite covers the most important pure logic (enums, range checks, Luhn validation, translation integrity) and several regression cases, but a full independent user testing session with real doctors and patients would reveal things that I cannot see from the developer side, like whether the medical examination tab order matches a doctor's actual workflow or whether patients understand the difference between the three payment methods without extra explanation.

Some features were descoped due to time. There is no native mobile application. There is no integration with external electronic health record (EHR) systems. There is no AI transcription of the video call. Analytics and usage reporting are limited to basic audit logs. The audit log admin view itself is functional but basic — it shows who did what and when, but it does not group events into sessions or visualize trends.

### Future Scope

The most useful next step is a Flutter mobile application for patients. Most people book appointments and join video calls from a phone, not a laptop, and a native app would allow push notifications to work reliably, background call reminders, and eventually a way for patients to take a photo of a test result and attach it to their booking before the consultation.

The next step after that is a real payment integration. Iyzico is partially wired into the codebase already because the project is deployable in Turkey where Iyzico is a common choice. Extending the prototype credit-card flow to use Iyzico or Stripe in production, and storing the tokenized payment method so returning patients do not have to re-enter their card, would be a significant quality-of-life improvement.

On the clinical side, adding AI transcription of the video consultation would make the prescription step faster. Right now the doctor has to type everything from memory at the end of the call. If the call were transcribed in real time and the medicines and tests were extracted automatically into the examination form, the doctor could focus on the patient during the call instead of typing. Whisper running on the server would make that feasible without sending audio to a third party, which matters for patient confidentiality.

Further ahead, a clinic dashboard with aggregate metrics (average consultation length, no-show rate, revenue per specialty, patient retention) would make the system attractive for clinic owners, not just individual doctors. And an insurance-claim integration would remove the last paper step for patients who get reimbursed.

## 5.6 Conclusion

This project started with the idea that patient and doctor should not have to be in the same room for a follow-up, and it ended with a deployed, working, multilingual telemedicine platform. It is not a complete product ready to ship to thousands of users, but the core flow runs end to end: a patient can find a doctor, book a slot, pay for it, meet over video, receive a prescription, and keep the record of the consultation. The doctor can manage their schedule, conduct the call, fill in the examination, and sign off on the prescription, all from one browser session.

Beyond the technical result, the project was a significant learning experience. Working with a modular Laravel architecture across fifteen modules, self-hosting a Jitsi Meet stack, designing a multi-guard authentication system, writing a custom composer CI pipeline with a translations integrity check, and iterating on the UI until the medical examination page felt calm instead of overwhelming — none of these are things that classroom exercises fully prepare you for. The experience of owning a project from database schema to live VPS deployment, and being the person who fixes the nginx config when the iframe refuses to load at 2 am, is valuable in a way that is hard to replicate any other way.

The skills developed through this project — Laravel 12, Livewire 3, Jitsi Meet self-hosting, nginx reverse proxy configuration, MySQL, Redis, Reverb WebSockets, Spatie Permissions and Translatable, GitHub Actions CI, PHPStan, Laravel Pint, and the general discipline of shipping a large codebase without a team to catch your mistakes — are all directly relevant to a software engineering career. More importantly, the project proved to me that a one-person team can actually deliver a serious application if the scope is controlled and the architecture stays disciplined. The Doctor System is something I intend to keep developing after the module is finished, because telemedicine is a real problem with a growing audience, and the gap that exists for a multilingual, Arabic-first, self-hostable platform is not going to close itself.
